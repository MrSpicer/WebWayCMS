# Known Issues

Findings from the 2026-10 full code and functionality review of WebWayCMS. All **High** and **Medium**
severity issues have been fixed (see "Resolved" at the bottom); the Medium findings were reconfirmed
against the post-refactor codebase on 2026-10-29 and closed the same day. Low findings are documented
here as accepted risks / backlog items.

## Medium

None currently open. (M9 below was re-reviewed and stands as intentional.)

**Note on M9:** The committed admin password in the TestHost is **intentional**. The TestHost is a
development-only test environment that will never be deployed and requires a known account for
automated and manual testing. This is not a security issue; do not flag it in future reviews.

## Resolved (fixed during this review)

| # | Finding | Fix |
|---|---------|-----|
| H1 | Forwarded headers trusted from every client (`KnownProxies.Clear()` / `KnownIPNetworks.Clear()`) → per-IP rate-limit bypass and IP spoofing | `CmsHttpInfrastructureRegistration.ConfigureForwardedHeaders` keeps the framework's loopback-only trust list by default; a host opts in with `ForwardedHeaders:KnownProxies` / `KnownIPNetworks`, or `TrustAllProxies` when the proxy address isn't stable (the shipped docker-compose sets it — nginx runs in its own container). Upgrade note in `docs/architecture/13-security.md` → Forwarded headers |
| H2 | `CMSRouteService.UpsertAsync` delete-then-insert not atomic — failed insert permanently deleted the owner's previous route row | Delete + insert share one transaction; on `DbUpdateException` the transaction is rolled back and tracked entities are cleared, so the previous route row survives |
| H3 | Failed republish rollback (`PageModel.PublishPageAsync`) left the page with zero published versions | `PublishAsync` reports the version it archived (`ContentWriteResult.DisplacedVersionId`); on route-registration failure `PublishPageAsync` calls `IContentStore.RevertPublishAsync(nodeId, publishedVersionId, displacedVersionId)`, which undoes only that publish (demote, then re-promote the displaced version, in one transaction). A publish that changed nothing (page already live, only zone drafts pending) is not reverted, and a page that was offline stays offline |
| H4 | Widget `ComponentPropertiesJson` saved without rich-text sanitization — stored XSS sink for widgets declaring `RichText` config fields | `WidgetConfigurationJson.Sanitize` rewrites only the config type's rich-text values in place (other keys kept, relaxed escaping, unreadable JSON fails closed to `{}`) on every zone-item write: the zone editor API and the child handler (admin form, MCP, seeder, restore) |
| M1 | In-place draft saves had no concurrency backstop — concurrent saves silently last-write-wins | Made moot by copy-on-write versioning (every save mints a version) and closed at three layers: the in-code `expectedVersionNumber` check, `DbUpdateException` → `StaleVersionMessage` mapping in `ContentStore`, and the `UX_ContentVersion_Number` unique index `(NodeId, Culture, Segment, VersionNumber)` as the DB backstop for the version-number race |
| M2 | `DeleteVersionAsync` could delete a Published version (only guarded on version number, not State) — silently unpublishes live content while route rows keep resolving | `ContentStore.DeleteVersionAsync` refuses any version whose `State == Published` (unpublish first; the version then deletes as an ordinary Archived row). Verified the zone-delete stray-version path only deletes non-published strays |
| M3 | Zone-tree deletion was multi-step with no transaction — partial failure left unreachable orphan subtrees | All deletion paths funnel through `ContentDeleteService`, which wraps the whole containment cascade (deepest first) in one `ICmsTransaction`; the multi-step `DeleteZoneCoreAsync`/`DeletePageZonesAsync` internals now only run inside it, and nested store writes join the ambient transaction |
| M4 | `FormProperty` `Min`/`Max`/`MaxLength`/`Pattern` were never enforced server-side — MCP writes and seed files could violate them | `ModelValidator` now enforces the `FormProperty` bounds on upsert view-model fields (at the shared save choke point), and the widget registries' `ValidateConfiguration` is wired into every zone-item save path, the zone editor API included (it was dead code; page configuration was already validated). It validates the payload before relation ids are stripped (so a required `[ContentRelation]` field such as ContentBlock's counts as set), only the fields of the item's effective display mode, and an empty payload as `{}`. The bounds live once in `FormPropertyConstraints`, with HTML `pattern` semantics (empty passes, whole-value match, match timeout) |
| M5 | 4000-char JSON columns had no pre-save length check — overflow became a raw DB exception; seed items with overflow retried forever | `WidgetConfigurationJson.LengthError` guards `ComponentPropertiesJson` (zone-item handler + zone editor API) and page `ConfigurationJson` (both page save paths) with a friendly validation error before the store is touched. (Item `MetadataJson` was already guarded by `WidgetMetadataJson.Normalize`.) The seeder logs a permanent field-error save at Error, naming it unfixable by retry |
| M6 | Seeder: failed publish after successful first-time save duplicated the item on every boot (ledger written only after publish) | The top-level path now records the ledger as soon as the node exists, with the **publish-pending** hash (the lowercase form of the real uppercase-hex hash; same column, never equal to a real hash). The next boot retries only the publish against the same node — no re-save, so no new version per boot — unless the seed item changed (an ordinary update) or the node was deleted (re-created); only a successful publish records the real hash. Page-zone items use the same marker (they were recorded with an empty hash and re-saved every boot while their publish failed) |
| M7 | Unpublishing a page left its zone items' widget routes live (rows persisted; reachability was already closed by the transformer's containment-visibility 404) | `UnpublishPageAsync` now sweeps the page-tree items' widget route rows along with the page's own routes; a republish re-registers the live items, so the sweep is reversible |
| M8 | Zone-item ordinal minting raced (`Max+1` read-then-write, no unique index) in the add path | Every ordinal write — add, reorder, move (both zones), restore, layout remap — takes a `SELECT … FOR UPDATE` row lock on the zone's own version rows inside its transaction (they exist even in an empty zone; two zones are locked in id order). An add mints `MAX+1` under it; an order write re-reads the zone under it, fails as stale when a planned item changed since it was read (its renumber could otherwise be skipped on a stale ordinal), and appends any item an add committed meanwhile. No unique index was added deliberately — a reorder rewrites 1..n sequentially inside its transaction. Verified on Postgres: concurrent adds + moves into one zone leave ordinals 1..n with no duplicates |
| M10 | `LoginWith2fa` and 2FA verification endpoints not rate-limited — an unauthenticated TOTP/recovery-code guessing oracle (segment matching did not accidentally cover `LoginWith2fa` under the `/Login` prefix) | `AuthRateLimiting.LimitedPaths` now includes `LoginWith2fa`, `LoginWithRecoveryCode`, and the Manage `EnableAuthenticator` / `TwoFactorAuthentication` endpoints (same per-IP, per-endpoint-family fixed window) |
| M11 | Descendant page routes were not updated when a parent's URL changed; unpublishing a parent left `/parent/child` rows live | The URL-change half was fixed by `ReprojectDescendantsAsync` (live descendants' Derived routes re-projected from their published versions inside the publish transaction, collision rolls everything back). The unpublish half is closed in effect by the route transformer's containment-visibility 404 (a page hidden by containment reads null ⇒ 404); the stale child rows remain until republish |
| M12 | Widget routes were not recomputed on a page slug rename — the publish cascade registered routes only for *pending* zone items, so an already-live Article widget kept `/old-slug/{slug}` | `PageModel.PublishZoneDraftsAsync` re-derives widget routes for every live item in the page's zone tree when the page's route changed (a rename, a first publish, a republish), and otherwise for the live widgets inside a container the publish put live, so a publish that leaves the URL alone touches only what it published. The rows of published items the page does not show — removed ones and widgets under a removed container — are swept in one batched delete |
| M13 | Deleting an article list failed (silently) for an article moved to another list — its historical versions still held the `Restrict` FK to the list | Content relations phase 1: the list is a version-owned containment relation with no DB FK on the target, and the delete cascade (`ContentDeleteService`) consults only current draft and published versions, so the moved article is left alone and the list deletes. Verified on the integration host |
| L8 | `GenericPageConfiguration.Meta`/`Style` stored XSS via `@Html.Raw` | `GenericPageConfiguration.SanitizedForRender()` (both page controllers) applies `HeadMarkupSanitizer` at render time: a `<meta>`/`<link>`-only allow-list for `Meta`, and `</` → `<\/` for `Style` (CSS kept verbatim). See `docs/architecture/13-security.md` |
